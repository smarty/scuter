Flush Error Integrity

Proposal · github.com/smarty/scuter · branch mikewhat/responsible-response · target release v0.8.0
Summary. When Flush fails today, the client can get a 200 status with an empty or partial body. The server keeps no record of the failure. This proposal makes each failure visible and gives the client a correct status where possible.
  • Flush encodes all JSON into a pooled buffer before it writes the status code. An encode failure becomes a clean 500 response.
  • Flush stages the headers that options add. It applies them only at commit. The 500 fallback discards them.
  • Flush reads the first 512 bytes of a streamed body before it commits the status. A first-read failure also becomes a clean 500 response.
  • scuter.WrapMonitoring wraps the router one time per service. Flush reports its errors to a caller-supplied monitor. The 339 existing call sites do not change.
  • The monitor does not get write errors from clients that disconnected.
  • Flush also returns the error, for tests and for special call sites.
  • A new Response.JSONOptions option takes json.Options values for JSON response bodies. The library supplies jsonv1.DefaultOptionsV1() first. Caller options come after and can override it.
  • ReadJSONRequestBody gets a variadic ...json.Options parameter with the same defaults and the same override order. All existing calls compile unchanged.
  • Flush always closes a body reader, also when a different body wins.
  • Flush releases caller values from the pooled config, and limits the retained buffer size.

The services move from v0.6.0 directly to v0.8.0. The only JSON change on the wire is the missing newline after a response body.

1. Background

1.1 The current Flush

func Flush(response http.ResponseWriter, options ...ResponseOption) {
	config := responseConfigs.Get()
	defer responseConfigs.Put(config)
	config.reset(response.Header())                // options write headers directly
	Response.With(options...)(config)

	response.WriteHeader(config.status)            // status is committed here

	if len(config.jsonErrors.Errors) > 0 {
		_ = json.MarshalWrite(response, config.jsonErrors)   // error discarded
	} else if config.dataJSON != nil {
		_ = json.MarshalWrite(response, config.dataJSON)     // error discarded; body may be partial
	} else if config.dataReader != nil {
		config.writeFromReader(response, config.dataReader)  // copy and close errors discarded
	} else if config.data.Len() > 0 {
		config.writeFromReader(response, &config.data)
	}
}

The function writes the status code first. Then it writes the body. After the status code goes out, the function cannot change it. The function also discards every error.

1.4 Severity

The services do not marshal unsupported types, and their handlers have high test coverage. But tests use clean fixtures. The encode failures that matter depend on the data, not on the types. With MarshalWrite, each of these data conditions leaves a partial body:

valid          → {"id":1,"name":"ok","ratio":0.5,"renewed":"2026-01-01T00:00:00Z"}
invalid UTF-8  → {"id":1     err: jsontext: invalid UTF-8 within "/name"
NaN            → {"id":1     err: unsupported value: NaN
+Inf           → {"id":1     err: unsupported value: +Inf
year 10000     → {"id":1     err: year outside of range [0,9999]
2000 rows, NaN in the last row → 56,180 bytes of JSON, then the error

An error from a custom MarshalJSON method has the same effect. The v1 options (jsonv1.DefaultOptionsV1()) do not change this for NaN, ±Inf, bad years, or marshaler errors. They only repair invalid UTF-8.

Effect by version

v0.6.0 uses the v1 Encoder.Encode, which encodes the full value before it writes. v0.7.0 uses the json/v2 MarshalWrite with default options, which writes while it encodes. No service uses v0.7.0.

Invalid UTF-8 is the most likely condition. The JSON decoder repairs strings that arrive in request bodies. These sources can still supply invalid UTF-8:

  • Database columns with a different character set.
  • Third-party APIs, for example payment gateways.
  • Code that cuts a string at a byte index, such as s[:n].

Exposure in the services

These counts cover the packages that call Flush:

  • time.Time: about 130 fields in 8 repos. A year outside 0–9999 needs bad data, so the risk is low.
  • float64: 2 Amount fields, in billing-context and reporting-context. NaN is unlikely.
  • Custom marshalers: 3, in authorization-context, payment-context, and reporting-context.
  • Strings: in almost every response. The risk depends on the source of each string.
  • Streamed bodies: about 10 calls to BodyFromReader or BodyWithAttachment.

A bad record fails the same way on every request. The likely symptom is one customer whose page never loads. The access logs and metrics show 200 for each of those requests, so nobody can find the cause.

The error wraps one or more of these sentinel errors. Flush uses errors.Join when more than one failure occurs (for example, a read error and a close error).

2.2 WrapMonitoring and the monitor interface

WrapMonitoring wraps an http.Handler. For each request, it wraps the ResponseWriter in a small monitoredWriter. This writer holds the request and the monitor. It also has an Unwrap method, so http.ResponseController still finds the inner writer.

When Flush has an error, it walks the Unwrap chain of its ResponseWriter. If it finds a monitoredWriter, that writer sends the error to the monitor. If it finds none, Flush only returns the error. Other middleware between WrapMonitoring and the handler does not break this, if that middleware also has Unwrap.

The monitor is any value that implements the unexported monitor interface. The interface has one method now. It can get more methods in later versions.

// monitor receives reports from Flush. It may gain methods in future versions.
type monitor interface {
	FlushFailed(request *http.Request, err error)
}

// WrapMonitoring wraps next so that Flush reports its errors to monitoring, together with the request.
// Write errors that occur after the client disconnects are not reported.
// A nil monitoring returns next unchanged.
func WrapMonitoring(next http.Handler, monitoring monitor) http.Handler {
	if monitoring == nil {
		return next
	}
	return http.HandlerFunc(func(response http.ResponseWriter, request *http.Request) {
		next.ServeHTTP(&monitoredWriter{ResponseWriter: response, request: request, monitoring: monitoring}, request)
	})
}

type monitoredWriter struct {
	http.ResponseWriter
	request    *http.Request
	monitoring monitor
}

func (this *monitoredWriter) Unwrap() http.ResponseWriter { return this.ResponseWriter }

func (this *monitoredWriter) report(err error) {
	if err = withoutDisconnects(this.request, err); err != nil {
		this.monitoring.FlushFailed(this.request, err)
	}
}

Client disconnects

When a write to the connection fails, net/http cancels the request context. The monitored writer uses this signal:

  • If the request context is not canceled, the monitor gets the full error.
  • If the request context is canceled, the writer removes each ErrFlushWrite part from the error. The monitor gets the rest, if any.

Thus the monitor still gets write errors from bugs, such as http.ErrBodyNotAllowed on a 204 response. The return value of Flush keeps all parts, including disconnects.

net/http buffers the first few kilobytes of each response. A disconnect during a small body shows only after the handler returns, so Flush never sees it.

Installation

A service installs the monitor at the router, for example in subscription-context/http/1_http_routes.go:

type flushLogger struct{ logger app.Logger }

func (this flushLogger) FlushFailed(request *http.Request, err error) {
	this.logger.Printf("[WARN] %s %s: %v", request.Method, request.URL.Path, err)
}

return scuter.WrapMonitoring(meta.NewHTTPHandler(httprouter.RequireNew(...)), flushLogger{logger: logger})

2.3 Header staging

Options do not write to response.Header() directly. Each header option appends an operation to a pooled list in the config. An operation holds a key, a value, and one of two actions: add or set. At commit, Flush replays the list on response.Header() in order, then writes the status.

  • Header, ContentType, and JSONContentType record an add action, as they do today.
  • JSONBody, JSONError, JSONErrors, and BodyWithAttachment record a set action, as they do today.
  • Headers that middleware wrote before Flush stay in response.Header(). The replay changes them in the same way as today.

Thus the result is the same as today on the success path. The 500 fallback discards the list, so headers such as Location, ETag, and Content-Disposition do not reach a 500 response.

type headerOperation struct {
	key     string
	value   string
	replace bool
}

func (this *responseConfig) commit(response http.ResponseWriter) {
	header := response.Header()
	for _, operation := range this.headers {
		if operation.replace {
			header.Set(operation.key, operation.value)
		} else {
			header.Add(operation.key, operation.value)
		}
	}
	response.WriteHeader(this.status)
}

2.4 Encode before commit, with a fallback

Flush encodes JSON into the pooled config.data buffer. It commits only after encoding succeeds. If encoding fails, Flush does these steps:

  1. It discards the staged header operations.
  2. It stages a set action for a JSON Content-Type.
  3. It sets the status to 500.
  4. It replaces the buffer with a precomputed body for ErrInternalServerError.
  5. It returns the encode error wrapped with ErrFlushEncode.

The package computes the fallback body one time, at initialization, with the library default options. Thus the fallback path has no encode step that can fail.

2.5 JSON options

A new option, Response.JSONOptions, takes json.Options values. Flush uses them when it encodes a JSONBody value or the JSONError/JSONErrors document. The existing JSON options do not change.

  • The library supplies jsonv1.DefaultOptionsV1() first. Thus the default output is the v0.6.0 wire format, without the trailing newline.
  • Values from Response.JSONOptions come after the library defaults, in the order that the options are applied. A later value overrides an earlier value.
  • The position of JSONOptions relative to JSONBody in the option list does not matter. Flush encodes after it applies all options.
  • A future version can remove the library defaults. Callers that need v1 behavior can then supply jsonv1.DefaultOptionsV1() themselves.
var defaultJSONOptions = jsonv1.DefaultOptionsV1()

// JSONOptions supplies options for encoding JSONBody and JSONError(s). Flush applies them after the
// library defaults (currently the encoding/json v1 behavior), so they can override those defaults.
func (responseSingleton) JSONOptions(options ...json.Options) ResponseOption {
	return func(config *responseConfig) { config.jsonOptions = append(config.jsonOptions, options...) }
}

Request decoding

ReadJSONRequestBody gets a trailing variadic parameter. It decodes with the library defaults first, then with the caller's options. The order and the override rules are the same as for responses.

func ReadJSONRequestBody(request *http.Request, v any, options ...json.Options) (ResponseOption, bool) {
	if !isJSONContent(request) {
		return Response.JSONErrors(http.StatusUnsupportedMediaType, ErrUnsupportedRequestContentType), false
	}
	if err := json.UnmarshalRead(request.Body, &v, defaultJSONOptions, json.JoinOptions(options...)); err != nil {
		return Response.JSONErrors(http.StatusBadRequest, ErrInvalidRequestJSONBody), false
	}
	return nil, true
}

A trailing variadic parameter keeps each existing call valid. The 11 services call ReadJSONRequestBody 102 times, always with two arguments. No code uses it as a function value, which is the only use that the change can break.

2.6 Streamed bodies

  • Peek. Flush reads up to 512 bytes into a fixed array in the pooled config, before it commits. A read error here causes the same 500 fallback as in 2.4. (512 bytes is also the size that net/http uses to detect a content type.)
  • Commit and copy. After a good peek, Flush commits, writes the peeked bytes, and copies the rest.
  • Classify. A small wrapper on the reader records read errors. After the copy, a recorded read error gives ErrFlushRead. Any other copy error gives ErrFlushWrite.
  • Close. A deferred call closes config.dataReader if it implements io.Closer. The call runs also when a JSON body or error wins. This fixes G4.

A read failure after the peek still cuts the body, because the status is already committed. Scuter does not abort the connection. Flush reports and returns ErrFlushRead, and the caller decides what to do.

2.7 Pool hygiene

A release method runs before Put. It does these steps:

  • It sets dataJSON and dataReader to nil.
  • It clears the header operations and the JSON options.
  • It replaces data with a new buffer if the capacity is more than 64 KiB.

Thus one large response does not keep a large buffer in the pool.

2.8 Flow inside Flush

2.9 Code sketch

This sketch shows the shape. It is not final code.

var (
	ErrFlushEncode = errors.New("scuter: encode response body")
	ErrFlushWrite  = errors.New("scuter: write response body")
	ErrFlushRead   = errors.New("scuter: read response body source")
	ErrFlushClose  = errors.New("scuter: close response body source")
)

// Flush applies the options, which may be supplied in any order, to the provided ResponseWriter.
// Flush encodes JSON bodies before it writes headers and the status code. If encoding fails, Flush
// sends a 500 response with ErrInternalServerError instead. Flush reports all errors it encounters
// to the nearest monitor (see WrapMonitoring) and also returns them, joined. Each one wraps an
// ErrFlush* sentinel.
func Flush(response http.ResponseWriter, options ...ResponseOption) (err error) {
	config := responseConfigs.Get()
	defer responseConfigs.Put(config)
	defer config.release()
	defer func() { reportFlushError(response, err) }()
	config.reset()
	Response.With(options...)(config)
	defer func() { err = errors.Join(err, config.closeReader()) }()

	switch {
	case len(config.jsonErrors.Errors) > 0:
		err = config.encode(config.jsonErrors)
	case config.dataJSON != nil:
		err = config.encode(config.dataJSON)
	case config.dataReader != nil:
		return config.stream(response)
	}
	return errors.Join(err, config.writeBuffered(response))
}

func (this *responseConfig) encode(v any) error {
	this.data.Reset() // JSON wins over BytesBody
	err := json.MarshalWrite(&this.data, v, this.jsonOptions...)
	if err == nil {
		return nil
	}
	this.fallback()
	return fmt.Errorf("%w: %w", ErrFlushEncode, err)
}

func (this *responseConfig) fallback() {
	this.headers = this.headers[:0]
	this.setHeader(headerContentType, jsonContentType)
	this.status = http.StatusInternalServerError
	this.data.Reset()
	_, _ = this.data.Write(fallbackBody) // bytes.Buffer.Write never fails
}

The deferred calls run in reverse order. Thus closeReader adds its error first, and reportFlushError then sees the complete error.

2.11 Not included

  • Content-Length on each buffered body. A known length helps a client detect a cut body. But net/http already sets Content-Length on small bodies (under about 2 KB) when the handler does not flush. A new header on every response also breaks service tests that compare full header sets.
  • An abort of the connection after commit. Scuter does not call panic(http.ErrAbortHandler). The caller can act on the returned ErrFlushRead.

3. The role of scuter

Agents now write most handler code. Plain net/http handlers are an alternative to scuter. Scuter stays, for the reasons below.

Reasons to keep scuter

  • One fix, many handlers. The defects in this proposal sit behind 339 handlers. A new scuter version fixes all of them.
  • Plain handlers repeat the defects. The most common Go idiom is w.WriteHeader(code) and then json.NewEncoder(w).Encode(v). This idiom has G1 and G2. Agents learn from that idiom.
  • Review cost stays high. Agents make code cheap to write. Humans still review, audit, and change that code. A fix in 339 different blocks needs 339 reviews.
  • Agents copy local patterns. A small, repeated vocabulary gives code with low variance. Low variance makes diffs easy to review.
  • Pure handlers. The serveHTTP(request) ResponseOption shape keeps handlers free of IO. The sales-context tests use Flush as a test oracle.

Limits of scuter

  • Less typing has no value now. Helpers that only save keystrokes, such as Response.Header and ContentType, add little. They also cost little.
  • The standard library covers some helpers. Go 1.22 ServeMux patterns and request.PathValue cover ReadPathElement. This helps only if httprouter supports path values, or the services move to ServeMux.
  • Agents know net/http better. Training data has much net/http code and no scuter code. But scuter is small, and every repo shows its patterns.
  • A library can hide defects. G1 is inside scuter. But it is in one place, and one review finds it.
Direction. Scuter is the one place for the rules that each HTTP response must follow. It owns the response commit, the request decode, the error document, and the test helpers. A separate change can remove helpers that the standard library covers.

4. Trade-offs

  • A service without WrapMonitoring still loses errors. Existing call sites compile without change and ignore the return value. Only a service that installs a monitor gets reports.
  • Two report paths. A call site that checks the return value, in a service with a monitor, reports the error two times. The README must say: use the monitor for reports, and use the return value only to act on the error.
  • The monitor interface is unexported. The documentation for WrapMonitoring shows the parameter type monitor, which callers cannot name. The README and the doc comment must list the method set.
  • A new interface method breaks monitors. When monitor gets a method, each service's monitor type stops compiling until it adds that method. This is acceptable at v0.
  • The disconnect filter depends on net/http. It uses the context cancellation that net/http does on a failed connection write. A different server, or a wrapper that replaces the request context, can change this.
  • The wrapper hides optional interfaces. A direct type assertion such as w.(http.Flusher) fails on a monitoredWriter. http.ResponseController works because of Unwrap. No service has such a direct assertion.
  • One allocation per request. WrapMonitoring allocates one monitoredWriter for each request. A pool can remove this, if a profile shows a need.
  • No test in each service proves the wiring. Scuter's tests cover WrapMonitoring. In each service, a reviewer confirms the wiring by reading the diff.
  • The v1 defaults keep the v1 weaknesses. Invalid UTF-8 is silently replaced in both directions. Request names match without case, and a duplicate name silently replaces the earlier value. A service can change each of these with Response.JSONOptions or the options of ReadJSONRequestBody.
  • More memory for large JSON bodies. The full encoded body stays in memory until the write. The 64 KiB retention limit keeps the pool small, but the peak memory for one request is the body size.
  • No sendfile for *os.File bodies. The peek and the read-recording wrapper hide the concrete file type from net/http. The server then copies through user space. This matters only for large file downloads.
  • The fallback body is fixed. The caller cannot choose a different error for the fallback.
  • Joined errors have more than one line. errors.Join puts a newline between errors. Single-line log formats show this as a line break.

Out of scope

  • Response.ContentType records an add action. Two calls give two Content-Type values. JSONBody records a set action.
  • Response.StatusCode(0) or another invalid code makes net/http panic in WriteHeader.
  • A move of the services to the json/v2 default wire format.
